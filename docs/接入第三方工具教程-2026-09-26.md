# 接入第三方工具教程

> 本文是独立开发者维护的技术配置说明，与 OpenAI、Anthropic、Google、xAI、DeepSeek、MiniMax 或其他模型厂商不存在官方关联、投资、赞助或合作关系。文中商标和产品名称仅用于协议兼容性说明。
> 本仓库不提供、不代售任何 API 服务或充值通道。
> 使用第三方服务前，请自行核对服务条款、隐私政策、价格和可用性。

本文以 NuoAPI 这类第三方 AI 网关为例，按**工具类型**分别说明四类工具怎么接：图形客户端、命令行、IDE 插件与智能体、Provider 管理器。

每一类只讲它自己的填法。协议原理、Base URL 与完整请求地址的区别，统一见[《AI 模型 API 协议科普》](AI模型API协议科普-2026-10-12.md)，本文不重复解释。

> 文中的地址夹具为 [`nuoapi.net`](https://nuoapi.net)（具体模型名按「分组」筛选见[模型广场](https://nuoapi.net/model-plaza)）；换用其他网关时只需整体替换地址，配置方法不变。

不同工具的菜单名称和配置字段可能随版本变化，最终以目标工具当前文档和账户控制台显示为准。

### 1.1 准备三个值

接入前准备：

1. API Key：从服务控制台创建，使用专门的测试 Key。
2. 模型名：从当前账户可见的模型列表或模型广场复制，不要凭印象填写。页面快照里，抄名字用[《模型广场清单（10-25）》](模型广场清单-2026-10-25.md)。[10-18](模型广场清单-2026-10-18.md) 与 [10-12](模型广场清单-2026-10-12.md) 只是历史窗口，不是现价。
3. 协议地址：按第 1 节选对 Base URL，不要把不同协议的地址混用。

API Key 只放在本机环境变量或工具的凭据存储中。不要提交到 Git、截图、公开 Issue、前端 JavaScript 或 CI 日志。示例文件只使用：

```text
YOUR_NUOAPI_API_KEY
```

## 2. 命令行客户端：先安装 Node.js 与 CLI

图形界面客户端（Cherry Studio、ChatBox、LobeChat 等）无需本节，直接跳到第 3 节。要使用 Claude Code、Codex CLI、Gemini CLI 这类命令行工具，先装 Node.js，再用 npm 装对应 CLI。

### 2.1 安装 Node.js

要求 Node.js 18 以上（建议 20 LTS 或更新），npm 随 Node.js 一起安装，无需单独装。

- **Windows**：推荐用 winget 一键安装：`winget install OpenJS.NodeJS.LTS`；也可到 <https://nodejs.org> 下载 LTS 安装包，双击按提示安装。
- **macOS**：`brew install node`（Homebrew），或到 nodejs.org 下载安装包。
- **Linux**：用发行版包管理器，或用 nvm 安装（便于切换版本）。

安装后**新开一个终端**验证（安装前已经打开的终端读不到新 PATH）：

```bash
node -v
npm -v
```

两行都出现版本号即可，例如 `v20.11.1` 和 `10.2.4`。只出版本号、不报错，再继续下一步。

Windows 上两个常见拦路虎（本机实测）：

- **PowerShell 执行策略拦截**：运行 npm 或全局命令时报"无法加载文件……因为在此系统上禁止运行脚本"，是 npm 生成的 `.ps1` shim 被拦。改用 `.cmd` 入口（如 `npm.cmd install ...`、`codex.cmd --version`），或执行一次 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` 放开当前用户的脚本权限。
- **装完仍提示命令不存在**：确认 Node.js 没装在临时目录；npm 全局 bin 目录（`npm config get prefix` 显示的路径）要在 PATH 内。安装后必须新开终端。

### 2.2 安装 CLI（按需安装，不必三个都装）

```bash
npm install -g @anthropic-ai/claude-code   # Claude Code
npm install -g @openai/codex@latest        # Codex CLI
npm install -g @google/gemini-cli          # Gemini CLI
```

分别用 `claude --version`、`codex --version`、`gemini --version` 验证，出现版本号即安装成功。提示 `command not found` 时，先按 2.1 节末尾两条排查（PATH 与执行策略），不要反复重装。

其余命令行 Agent 各有自己的安装方式，先按官方文档装好、能跑 `--version`，再进 [5.5 节](#55-其他命令行-agent)配置：

- **Grok Build**（xAI，命令 `grok`）：官方一键脚本 `curl -fsSL https://x.ai/cli/install.sh | bash`，脚本环境也可用 `npm install -g @xai-official/grok`。
- **OpenCode**（命令 `opencode`）：见[第 4 节](#4-图形客户端)与示例 [`../examples/opencode.json.example`](../examples/opencode.json.example)。
- **Pi**（earendil-works，命令 `pi`）：按官方仓库 <https://github.com/earendil-works/pi> 说明安装（npm 包名 `@earendil-works/pi-coding-agent`）。
- **MiniMax Code**（命令 `mcode`）：按官方仓库 <https://github.com/MiniMax-AI/minimax-code> 说明安装。
- **DeepSeek Harness**（命令 `dsh`）：`npx @deepseek-ai/dsh web`，或从官网 <https://www.deepseek.com/harness/> 下载桌面端。

装好 CLI 之后，再回到第 3 节判断你的环境怎么配置。

## 3. 通用配置载体

同一个协议，在图形界面、终端、容器里的"填法"不同。先判断你的工具跑在哪种环境。

### 3.1 图形界面（桌面客户端 / IDE 设置面板）

最常见也最简单：打开设置里的模型/提供商页面，按第 1 节速查表填三个值，保存后**完全退出并重新打开**客户端再测。注意：

- 提供方类型选 `OpenAI Compatible` / `Anthropic` / `Gemini` 等协议项，而不是找"NuoAPI"这个名字。
- 部分客户端有"Base URL"和"完整 URL/自定义协议"两种模式，按第 1 节速查表对号入座。

### 3.2 命令行：环境变量

先记住各协议面孔对应的常用变量名（具体变量名以工具文档为准）：

| 协议面孔               | 地址变量                                        | 密钥变量                   | 其他                                        |
| ------------------ | ------------------------------------------- | ---------------------- | ----------------------------------------- |
| OpenAI 两协议         | `OPENAI_BASE_URL=https://nuoapi.net/v1`     | `OPENAI_API_KEY`       | Codex 另有 `~/.codex/config.toml` 写法（第 5.2 节） |
| Anthropic Messages | `ANTHROPIC_BASE_URL=https://nuoapi.net`     | `ANTHROPIC_AUTH_TOKEN` | 根地址，不带 /v1                                |
| Gemini CLI         | `GOOGLE_GEMINI_BASE_URL=https://nuoapi.net` | `GEMINI_API_KEY`       | 另设 `GEMINI_MODEL=模型广场模型名`                 |

**Windows PowerShell：**

```powershell
# 仅当前窗口生效（临时）
$env:OPENAI_BASE_URL = "https://nuoapi.net/v1"
$env:OPENAI_API_KEY = "YOUR_NUOAPI_API_KEY"

# 写入当前用户环境变量（永久，重开终端生效）
[Environment]::SetEnvironmentVariable("OPENAI_BASE_URL", "https://nuoapi.net/v1", "User")
[Environment]::SetEnvironmentVariable("OPENAI_API_KEY", "YOUR_NUOAPI_API_KEY", "User")
```

**macOS / Linux / WSL（Bash 或 Zsh）：**

```bash
# 仅当前终端生效（临时）
export OPENAI_BASE_URL="https://nuoapi.net/v1"
export OPENAI_API_KEY="YOUR_NUOAPI_API_KEY"

# 永久：写进 shell 配置后 source（zsh 用户换成 ~/.zshrc）
echo 'export OPENAI_BASE_URL="https://nuoapi.net/v1"' >> ~/.bashrc
echo 'export OPENAI_API_KEY="YOUR_NUOAPI_API_KEY"' >> ~/.bashrc
source ~/.bashrc
```

注意：Windows 上通过"系统属性→环境变量"或 `SetEnvironmentVariable` 设置后，**已经打开的终端和 GUI 程序读不到新值**，必须新开终端、或从开始菜单重新启动 GUI 程序。

### 3.3 命令行：配置文件

支持配置文件的 CLI（Codex、Claude Code、Gemini CLI 等）优先用配置文件，可随项目模板分发（只提交占位值）。路径按操作系统区分：

| 工具配置           | Windows                                       | macOS / Linux                                                     |
| -------------- | --------------------------------------------- | ----------------------------------------------------------------- |
| Codex          | `%USERPROFILE%\.codex\config.toml`            | `~/.codex/config.toml`                                            |
| Claude Desktop | `%APPDATA%\Claude\claude_desktop_config.json` | `~/Library/Application Support/Claude/claude_desktop_config.json` |
| Shell 环境配置     | PowerShell `$PROFILE`                         | Bash `~/.bashrc` / Zsh `~/.zshrc`                                 |

Windows 上该目录可能是隐藏目录，可在 PowerShell 中 `mkdir "$env:USERPROFILE\.codex" -Force` 后再编辑；路径含空格或中文时加引号。

### 3.4 Docker 容器与 CI

容器和 CI 里没有"设置面板"，统一走环境变量注入，Key 只能来自密钥管理：

- `docker run`：`-e OPENAI_BASE_URL=https://nuoapi.net/v1 -e OPENAI_API_KEY`（值从宿主机环境带入，不写进镜像）。
- `docker compose`：用 `environment:` 或 `env_file:`，env 文件加入 `.gitignore`。
- CI（GitHub Actions 等）：把 Key 存进仓库/平台的 Secrets，在步骤里映射成环境变量；不要写在 workflow 明文里。
- 容器内访问不到 `127.0.0.1` 上的本地代理时，地址要换成宿主机可达地址（如 `host.docker.internal`），但中转站地址是公网域名，不受此影响。

## 4. 图形客户端

适用于 OpenCode、Cherry Studio、LobeChat、Cursor、Roo Code、Cline、Aider 以及其他提供 OpenAI Compatible 选项的工具（含经中转站使用 Grok 模型的场景）。

在工具设置中填写：

```text
Provider:   NuoAPI
Base URL:   https://nuoapi.net/v1
API Key:    YOUR_NUOAPI_API_KEY
Model:      MODEL_NAME_FROM_MODEL_PLAZA
```

保存后完全退出并重新打开客户端，发送最小测试消息：

```text
请只回复：连接成功
```

OpenCode 的 JSON 模板见 [`../examples/opencode.json.example`](../examples/opencode.json.example)。如果工具要求填写完整路径，通常可从以下入口开始核对：

```text
POST https://nuoapi.net/v1/chat/completions
```

但不要仅凭 HTTP 200 判断高级能力可用。工具调用、流式输出、图片、联网搜索和长上下文都需要分别检查响应字段和实际结果。

### 4.1 桌面客户端逐个配置

> 下列入口与字段来自各产品公开文档/官方公告，**取证窗口 2026-10-06**，界面会随版本变化，以你本机版本为准。接完都按[第 10 节](#10-最小验收流程)做最小验收。

#### ZCode（智谱 Z.ai 桌面端）

官方支持添加任意 Anthropic / OpenAI 兼容服务（含本地部署）：

1. 点对话框里的模型名 → 列表底部「管理模型」，进入「Agents 设置 / 模型」面板；在左侧提供商列表底部点「添加提供商」。
2. 名称自取；地址二选一（也可都填）：
   - OpenAI 兼容 Base URL：`https://nuoapi.net/v1`
   - Anthropic 兼容 Base URL：根地址 `https://nuoapi.net`（不带 `/v1`）
3. 填 NuoAPI 的 API Key；确认地址后新版会自动拉取模型列表，也可用「添加模型」手填模型 ID（照抄模型广场）。
4. 打开启用开关，回模型选择器选中该模型后测活。

两个注意点：

- 代理在「设置 → 常规 → HTTP 代理」单独配置，**该字段留空表示直连，不读取 `HTTP_PROXY` 等系统变量**，改完代理要重启应用。
- 另有命令行 zcode 使用 `~/.zcode/v2/provider_config.json`（协议字段 `openai-chat-completions` / `openai-responses` 加 `baseUrl`）的说法来自第三方仓库文档，**C 级、未单点证实**；桌面端图形配置才是官方文档明确记载的路径。

依据：ZCode 官方文档《Connect Models》《API key 配置》（zcode.z.ai，取证窗口 2026-10-06）。

#### WorkBuddy（腾讯云桌面 Agent）

WorkBuddy 的「自定义 API」是 OpenAI Chat Completions 形态，且**接口地址要填完整路径**，不像多数客户端那样只填前缀：

1. 左下角账户（头像）→ 设置 → 模型 → 自定义模型 → 添加模型；提供商选「自定义 / Custom」。
2. 接口地址：`https://nuoapi.net/v1/chat/completions`
3. API Key：NuoAPI Key（官方说明配置参数含 Key 仅保存在本地 `~/.workbuddy/models.json`，不上传云端）。
4. 模型名称：照抄模型广场的精确模型 ID（该字段就是服务端 `model` 参数，**不支持自定义别名**）。
5. 高级工具（工具调用 / 图片输入 / 推理模式）按模型真实能力勾选，不要无脑全勾；保存后在模型选择器选中，列表里不出现就重启 WorkBuddy。

也可直接写配置文件 `~/.workbuddy/models.json`（Windows 为 `%USERPROFILE%\.workbuddy\models.json`），文件必须存成 **UTF-8 无 BOM**：

```json
{
  "models": [
    {
      "id": "MODEL_NAME_FROM_MODEL_PLAZA",
      "name": "MODEL_NAME_FROM_MODEL_PLAZA",
      "vendor": "Custom",
      "url": "https://nuoapi.net/v1/chat/completions",
      "apiKey": "YOUR_NUOAPI_API_KEY",
      "supportsToolCall": true,
      "supportsImages": false
    }
  ]
}
```

依据：腾讯云《WorkBuddy Enterprise 模型配置》（更新于 2026-09-07）、腾讯云国际站 TokenHub 接入 WorkBuddy 文档（2026-09-21）与腾讯云开发 CloudBase 文档。

#### Marvis（腾讯操作系统级 AI 管家）

- 入口：设置 → 模型管理 → 自定义模型（该功能 2026-09-01 上线，Mac / Windows / iOS / 安卓 / iPad 均可用）。
- 界面内置腾讯云、DeepSeek、阿里云等快捷项，并保留「自定义模型」入口，可接入采用行业通用接口标准的第三方服务与本地部署模型；自定义模型走**你自己的账户**计费，不占用每日免费额度；配置绑定账号、跨设备同步。
- **字段级填法证据不足**：截至取证窗口官方只发布了功能新闻，没有公开字段文档。先按 OpenAI 兼容套路试：界面要「基础地址 / Base URL」就填 `https://nuoapi.net/v1`，要「完整接口地址」就填 `https://nuoapi.net/v1/chat/completions`，模型 ID 照抄模型广场；报 404 就在两种填法之间切换，并对照第 11 节错误表排查。

依据：科技日报 2026-09-01、新华网 2026-09-24、腾讯科技相关报道（B 级，可证实功能与入口存在；具体字段为推断，C 级）。

#### Cherry Studio（桌面客户端）

Cherry Studio 内置 60+ 家 Provider 模板，也能接任意 OpenAI / Anthropic / Gemini 兼容端点。接 NuoAPI：

1. 设置 → 模型服务 → 列表底部「+ 添加」，提供商名称自取（如 `NuoAPI`），类型选 `OpenAI`（要按 Anthropic 协议接就选 `Anthropic`）。
2. 填 API 密钥：NuoAPI Key；**API 地址**：`OpenAI` 类型填 `https://nuoapi.net/v1`，`Anthropic` 类型填根地址 `https://nuoapi.net`。
3. 模型管理里「+ 添加」手填模型 ID（照抄模型广场），或点「获取模型列表」自动拉取；点「检测」验证连接，打开右上角启用开关。

注意两点：

1. Cherry Studio 另有内置的 `New API` 服务商模板，它会把一个根地址按协议自动补上 `/v1` 或 `/v1beta`。**不要把 `/chat/completions` 这类完整路径粘进去。**
2. 只有中转站明确要求不带版本前缀时，才在地址末尾加 `#` 关掉自动拼接。

NuoAPI 是 sub2api 形态而非 New API 部署，通常用「自定义服务商」而不是 `New API` 模板。

依据：Cherry Studio 官方文档《模型服务》《自定义服务商》《New API》（docs.cherryai.com.cn），B 级，取证窗口 2026-10-12。

## 5. 命令行客户端

### 5.1 Claude Code 与 Claude 类工具

命令行的填法已拆到[《Claude Code：不要加 /v1》](Claude-Code-不要加v1-2026-10-18.md)：症状是 `404 page not found`，一份配置是根地址加 `ANTHROPIC_AUTH_TOKEN`，改完重开终端。本节不再放第二份配置。

VS Code / Cursor 插件不读那份环境变量，见 [5.4](#54-claude-code-编辑器插件vs-code--cursor)。

### 5.2 Codex CLI 与其他 Responses CLI

Codex 的填法已拆到[《Codex：关掉 WebSocket》](Codex-一直Reconnecting-2026-10-18.md)：症状是一直 `Reconnecting` 或日志出现 `wss://…/v1/responses`，一份配置是 `wire_api = "responses"` 且 `supports_websockets = false`，改完彻底退出再开。

同一工具若还支持 Chat Completions（`wire_api = "chat"` 一类取值），只有在 Responses 入口不通、且模型广场表明该模型走 Completions 时再切换，并在自己的记录里注明实际协议。不要混着试。

### 5.3 Gemini CLI

Gemini CLI 的填法已拆到[《Gemini CLI：platform is not gemini》](Gemini-CLI-platform-is-not-gemini-2026-10-18.md)：症状是 `400 platform is not gemini` 或改完仍无响应，一份配置是 `GOOGLE_GEMINI_BASE_URL` 只填根地址，改完重启 CLI。

### 5.4 Claude Code 编辑器插件（VS Code / Cursor）

Claude Code 的 **VS Code / Cursor 插件**与 [CLI 短页](Claude-Code-不要加v1-2026-10-18.md) 读配置的方式不同：

- CLI 读 shell 环境变量和 `~/.claude/settings.json`。
- 插件启动前先检查它自己的 VS Code 设置。

所以走插件的场景，地址和 Key 要写进 **`claudeCode.environmentVariables`**。打开命令面板运行 `Preferences: Open User Settings (JSON)`，加入：

```json
{
  "claudeCode.environmentVariables": [
    { "name": "ANTHROPIC_BASE_URL", "value": "https://nuoapi.net" },
    { "name": "ANTHROPIC_AUTH_TOKEN", "value": "YOUR_NUOAPI_API_KEY" },
    { "name": "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC", "value": "1" }
  ],
  "claudeCode.preferredLocation": "panel",
  "claudeCode.selectedModel": "MODEL_NAME_FROM_MODEL_PLAZA"
}
```

- `"name"` 字段是固定键名（不是 `key`）；`ANTHROPIC_BASE_URL` 填**根地址，不带 `/v1`**。
- `claudeCode.selectedModel` 是插件内选中的模型名，照抄模型广场的精确 ID。
- 只在命令面板里选了别的模型、却没配对地址，会继续走官方端点并触发登录——插件与 CLI 的配置不要混填。

依据：Anthropic 官方《Connect Claude Code to an LLM gateway》（code.claude.com/docs/en/llm-gateway-connect），B 级，取证窗口 2026-10-12。

#### dsh（DeepSeek Harness）

dsh 是 DeepSeek 官方开源的本地 Agent 运行时（npm 包 `@deepseek-ai/dsh`，命令名 `dsh`，含 Web UI、桌面端与 headless），以自定义 Provider 形式接入模型，采用「一切皆插件」（Cordis）架构。官方入口：

- 官网 / 桌面端下载：<https://www.deepseek.com/harness/>（提供 macOS Apple 芯片与 Windows 64 位安装包）
- 源码（MIT）：<https://github.com/deepseek-ai/deepseek-harness>
- 开发者文档：<https://deepseek-harness.github.io/deepseek-harness/>

需要 Node.js `^22.19.0` 或 `>=24.0.0`；官方声明仍为开发者预览，配置格式可能随版本变化。

Web UI（推荐）：

1. 在工作目录运行 `npx -y @deepseek-ai/dsh web`（全局安装用 `pnpm add -g @deepseek-ai/dsh`），打开后进入 Settings → Models → Add a custom provider。
2. Provider ID / 名称自取（如 `nuoapi`）；Base URL 填 `https://nuoapi.net/v1`；API protocol 选 `openai-completions`（覆盖面最广；`openai-responses` 只有部分模型接受）；填 NuoAPI Key。
3. 点 Fetch available models 拉取并勾选模型，Create provider 后回会话在模型选择器中选用。

也可直接编辑 `~/.dsh/settings.yaml`（Windows 为 `%USERPROFILE%\.dsh\settings.yaml`）：

```yaml
agent-default-model:
  provider: nuoapi
  model: MODEL_NAME_FROM_MODEL_PLAZA

llm-pi-ai:
  providers:
    nuoapi:
      api: openai-completions
      baseURL: https://nuoapi.net/v1
      apiKeyEnv: NUOAPI_API_KEY
      models:
        - id: MODEL_NAME_FROM_MODEL_PLAZA
```

Key 通过 `NUOAPI_API_KEY` 环境变量注入（用 Web UI 录入则写在同目录 `.credentials.yaml`），不要明文写进 yaml、截图或提交 Git。

Anthropic 系协议（`anthropic-messages`）的 Base URL 试填根地址 `https://nuoapi.net`。该形态下 dsh 具体如何拼路径**未单点证实**——拉取模型失败就退回 `openai-completions`。

依据：DeepSeek 官方站与仓库，以及阿里云百炼《DeepSeek Harness》接入文档，对应 dsh 0.1.2-rc.1 前后版本。

- 官方站：<https://www.deepseek.com/harness/>
- 仓库：<https://github.com/deepseek-ai/deepseek-harness>
- 文档站：<https://deepseek-harness.github.io/deepseek-harness/>

B 级，官方站取证窗口 2026-10-12。

#### Grok Build（xAI 终端编码 Agent）

Grok Build 是 xAI 官方的终端编码 Agent（命令 `grok`，含全屏 TUI、headless `-p` 与 ACP），把第三方模型作为 `[model.<名称>]` 段写进配置，支持 `chat_completions` / `responses` / `messages` 三种后端。

配置文件：`~/.grok/config.toml`（Windows 为 `%USERPROFILE%\.grok\config.toml`，根目录可用 `GROK_HOME` 覆盖）：

```toml
[model.nuoapi]
model = "MODEL_NAME_FROM_MODEL_PLAZA"   # 真正发给上游的模型 id
base_url = "https://nuoapi.net/v1"      # provider 端点
name = "NuoAPI"
env_key = "NUOAPI_API_KEY"              # 存放 Key 的环境变量
api_backend = "chat_completions"        # chat_completions | responses | messages

[models]
default = "nuoapi"
```

- Key 走 `env_key` 指定的环境变量（优先 `env_key`，不要明文写 `api_key`）；改完配置用 `grok inspect` 查看它发现到的配置源。
- `api_backend` 选错会 400 / 404：NuoAPI 的 OpenAI 面选 `chat_completions`，Messages 面选 `messages`，并注意根地址与 `/v1` 的差别（第 1 节）。
- 若要让 Grok 从网关拉模型列表，可另设 `GROK_MODELS_BASE_URL=https://nuoapi.net/v1` 与 `XAI_API_KEY`；但更符合本仓库 Key 隔离纪律的做法是 `env_key`。

依据：xAI 官方文档《Grok Build Settings》《Custom Models》（docs.x.ai/build/settings、docs.x.ai/build/overview）与 xAI 仓库用户指南 11-custom-models（B 级，取证窗口 2026-10-12）。

#### OpenCode（开源终端 Agent）

OpenCode 是 provider 无关的开源编码 Agent，示例见 [`../examples/opencode.json.example`](../examples/opencode.json.example)，第 4 节也有它的通用填法。

配置分三步：

1. 在 `provider` 里加一个 `nuoapi` 项，`npm` 用 `@ai-sdk/openai`。
2. `options.baseURL` 填 `https://nuoapi.net/v1`，`options.apiKey` 填 NuoAPI Key。
3. 在 `models` 里登记模型 id，并把 `model` / `small_model` 指到 `nuoapi/<模型 id>`。

CC Switch 里它属共存模式（[第 6 节](#6-provider-配置管理器cc-switch)），写入后要在 OpenCode 内选中该模型。

依据：本仓库示例 [`../examples/opencode.json.example`](../examples/opencode.json.example) 与 OpenCode 官方配置文档（B 级，取证窗口 2026-10-12）。

#### Claude Code Router（CCR，把 Claude Code 接到非 Anthropic 端点）

Claude Code Router 是一个**社区开源**代理。它在本机起一个小服务，把 Claude Code 发出的 Anthropic Messages 请求转换成目标 Provider 的协议（OpenAI Chat Completions、DeepSeek、Gemini 等）。

作用是让只认 Anthropic 协议的 Claude Code 也能用上 NuoAPI 的 OpenAI 兼容模型。

- 安装后以 `ccr code` 启动，它会注入 `ANTHROPIC_BASE_URL=http://127.0.0.1:3456` 指向本机代理。
- 配置文件 `~/.claude-code-router/config.json`（JSON5，支持注释与 `${ENV}` 插值）：

```json
{
  "Providers": [
    {
      "name": "nuoapi",
      "api_base_url": "https://nuoapi.net/v1/chat/completions",
      "api_key": "${NUOAPI_API_KEY}",
      "models": ["MODEL_NAME_FROM_MODEL_PLAZA"],
      "transformers": ["openai"]
    }
  ],
  "Router": {
    "default": "nuoapi,MODEL_NAME_FROM_MODEL_PLAZA",
    "background": "nuoapi,MODEL_NAME_FROM_MODEL_PLAZA"
  }
}
```

- `api_base_url` 填**完整**的 `chat/completions` 路径；`transformers`（新版也接受 `transformer.use`）指定协议转换器，OpenAI 兼容用 `openai`。
- `Router.default` 形如 `"provider,model"`；`background` / `think` / `longContext` 可分别指向不同模型。
- 改完配置用 `ccr restart` 生效；它只做协议转换，**不改变鉴权与计费**，Key 仍是 NuoAPI Key。

依据：CCR 官方仓库 <https://github.com/musistudio/claude-code-router>（`config.json` 的 Providers / Router / transformers）。

**社区项目、非厂商官方**；字段口径 B 级，取证窗口 2026-10-12。版本迭代快，以你安装版本的 README 为准。

#### Pi（earendil-works 极简编码 Agent）

Pi 是 earendil-works 的极简、可操纵编码 Agent（命令 `pi`），通过 `models.json` 接入任何兼容 OpenAI / Anthropic / Google 的服务。

配置文件：`~/.pi/agent/models.json`，Windows 为 `%USERPROFILE%\.pi\agent\models.json`。示例：

```json
{
  "providers": {
    "nuoapi": {
      "baseUrl": "https://nuoapi.net/v1",
      "api": "openai-completions",
      "apiKey": "$NUOAPI_API_KEY",
      "models": [
        { "id": "MODEL_NAME_FROM_MODEL_PLAZA" }
      ]
    }
  }
}
```

- `api` 可取 `openai-completions` / `openai-responses` / `anthropic-messages` / `google-generative-ai`；一个 provider 只用一种协议，NuoAPI 同时提供两种时要建两个 provider。
- `apiKey` 支持 `$ENV_VAR` 插值与 `!command`，用它引用环境变量，不要把明文 Key 写进 JSON；不写 `apiKey` 时改用 `/login` 或 CLI `--api-key`。
- 模型级 `contextWindow` / `maxTokens` / `input`（`text`、`image`）按模型真实能力填；只填 id 也能加载，但上下文与多模态能力没有声明。

依据：Pi 官方文档《Custom Providers》与 Pi 仓库 models 文档（pi.dev/docs/latest/custom-provider、github.com/earendil-works/pi，B 级，取证窗口 2026-10-12）。

#### MiniMax Code（mcode）

MiniMax Code 是 MiniMax 官方开源的终端编码 Agent（命令 `mcode`，支持插件与 MCP），通过 `mcode provider add` 或 TUI 的「+ Add 3rd-party provider…」接入自定义端点。命令行方式：

```bash
export MCODE_PROVIDER_API_KEY="YOUR_NUOAPI_API_KEY"
mcode provider add --name "NuoAPI" --base-url "https://nuoapi.net/v1" \
  --api-format openai-completions --model "MODEL_NAME_FROM_MODEL_PLAZA" \
  --api-key-env MCODE_PROVIDER_API_KEY --use
```

- `--api-format` 三选一：`openai-completions`、`openai-responses`、`anthropic-messages`；`--model` 可重复，`--use` 用第一个模型做连通测试并设为默认（测试失败则什么都不保存）。
- 自定义模型可用 `--context-limit` 与 `--output-limit` 声明上下文与输出上限（按服务端真实值填），`--api-key-env` 指向存 Key 的环境变量（不给时读 `MCODE_PROVIDER_API_KEY`）。
- 配置写入当前 profile 的 `config.yaml` 中 `custom_provider` 节点（`minimax_api` 保留给官方端点，不要混用）。鉴权头按格式自动选择：OpenAI 两协议发 `Authorization: Bearer`，`anthropic-messages` 发 `x-api-key`；**若走 NuoAPI 的 Messages 入口又需要 Bearer，须在 `config.yaml` 里显式加 header**（默认 `x-api-key` 头仍会一并发送，需服务端容忍）：

```yaml
custom_provider:
  nuoapi:
    options:
      apiKey: YOUR_NUOAPI_API_KEY
      baseURL: https://nuoapi.net
      headers:
        Authorization: Bearer YOUR_NUOAPI_API_KEY
    models:
      MODEL_NAME_FROM_MODEL_PLAZA: {}
```

依据：MiniMax 官方《MiniMax Code》CLI 文档（agent.minimax.io/docs/cli/configuration、/reference）与仓库 <https://github.com/MiniMax-AI/minimax-code>（B 级，取证窗口 2026-10-12）。

## 6. Provider 配置管理器：CC Switch

CC Switch 是一个开源图形工具，把多款命令行 Agent 的 Provider 配置放在同一个界面里管理，少手写 TOML、JSON 和环境变量。

- 官网：<https://ccswitch.io>
- 源码：<https://github.com/farion1231/cc-switch>

当前版本支持**十款工具**：Claude Code、Claude Desktop、Codex、Gemini CLI、Grok Build、OpenCode、OpenClaw、Hermes、Pi、MiniMax Code。

先记住它的边界：**CC Switch 只负责读写本机配置文件、切换或追加 Provider，不代理任何网络流量**。

目标 CLI 仍要先按[第 2 节](#2-命令行客户端先安装-nodejs-与-cli)装好并能正常运行（`claude --version` / `codex --version` / `gemini --version` 有输出）。

十款工具分两种写入模式，含义不同：

- **切换模式（Switch）**：Claude Code、Claude Desktop、Codex、Gemini CLI、Grok Build。点"启用"即把该 Provider 设为当前使用，工具同一时刻只读一份配置。
- **共存模式（Coexist）**：OpenCode、OpenClaw、Hermes、Pi、MiniMax Code。点"Add"（Pi 显示为 Enable / Remove）把该 Provider **追加**进工具自身配置，可同时保留多个，之后在该工具内再选具体模型。

### 6.1 安装 CC Switch

下载页（GitHub Releases）：<https://github.com/farion1231/cc-switch/releases>

- **Windows**：优先在 Assets 区下载最新 `.msi`，双击后按 Next / Install 安装，完成后从开始菜单搜索 CC Switch 打开。找不到 `.msi` 时下载 `.zip` 便携版，解压到任意目录后双击 `cc-switch.exe`。
- **macOS**：可用 Homebrew，或下载 Releases 中的安装包。
- **Linux**：按发行版选 `.deb` / `.rpm` / AppImage。

开始菜单里能找到并打开 CC Switch，就是安装完成。

### 6.2 从 NuoAPI 一键导入

1. 打开 NuoAPI 控制台的 API 密钥页面。
2. 找到要使用的 Key，点击"导入到 CCS"。
3. 浏览器提示"打开外部应用"时选择允许，CC Switch 会自动启动并带入该 Key 的配置。
4. 回到 CC Switch，确认对应工具标签下该 Provider 已被设为"当前使用"。

如果浏览器没有弹窗，或点了没反应，改用下面的手动方式。

### 6.3 手动添加 Provider

在 CC Switch 中点对应工具标签 → 点「+ 添加 Provider」→ 填地址、粘贴 NuoAPI Key。

保存后按该工具的模式收尾：切换模式点「启用」，共存模式点「Add」。

两种模式的差别：

- **切换模式**：CC Switch 直接接管该工具的配置。
- **共存模式**：只追加一个 Provider，模型要在工具内自己选。

地址按工具区分，与[第 1 节](#1-按工具类型选择)速查一致。

| 工具 | Provider 地址 | 模式 |
| --- | --- | --- |
| Claude Code | `https://nuoapi.net`（根地址，**不加 /v1**） | 切换 |
| Codex | `https://nuoapi.net/v1` | 切换 |
| Gemini CLI | `https://nuoapi.net`（根地址，即 `GOOGLE_GEMINI_BASE_URL`） | 切换 |
| Claude Desktop | 仅做模型映射，端点走 Cowork 自身设置，**本仓库未单点实测**（C 级） | 切换 |
| Grok Build | `https://nuoapi.net/v1` | 共存 |
| OpenCode | `https://nuoapi.net/v1` | 共存 |
| Pi | `https://nuoapi.net/v1` | 共存 |
| MiniMax Code | `https://nuoapi.net/v1` | 共存 |

OpenClaw 与 Hermes 的模板见 [`../examples/openclaw.json.example`](../examples/openclaw.json.example) 与 [`../examples/hermes.yaml.example`](../examples/hermes.yaml.example)。

注意：旧版教程此处写的是 `nuoapi.com`，那是旧站域名；新站一律使用 `https://nuoapi.net`（区别见 [FAQ 第 13 节](../FAQ.md#13-什么时候使用旧站域名)）。

Gemini 模型还要确认当前分组支持，并在工具配置里写对模型名。共存模式下，CC Switch 只把 Provider 追加进工具配置，**选哪个模型要在工具自身界面里完成**。

> 本轮核对：NuoAPI 官方文档的网页存档**整页仍使用 `nuoapi.com`**（来自旧/并行 `.com` 实例，当前无服务），属旧域名，**不要照抄**。本仓库的地址一律以 A 级实测的 `https://nuoapi.net` 为准；抄模型名用[《模型广场清单（10-25）》](模型广场清单-2026-10-25.md)，[10-18](模型广场清单-2026-10-18.md) 与 [10-12](模型广场清单-2026-10-12.md) 只是历史窗口。

### 6.4 保存后重启客户端

Provider 写入后，**完全退出并重新打开**对应的 CLI / 编辑器窗口。界面配置正确但 CLI 不生效，几乎都是客户端还在读旧配置。

两种模式的成功标志不同：

- **切换模式**：在 CC Switch 里点测试可用、且配置标记为"当前使用"即成功。
- **共存模式**：写入后还要回工具内 `/model`（或等价入口）选中该 Provider 的模型。

导入后不生效的排查见 [FAQ 第 10 节](../FAQ.md#10-cc-switch-导入后没有生效怎么办)。

## 7. IDE 插件与智能体

### 7.1 Cursor、Roo Code、Cline 与 Continue

Cursor、Roo Code、Cline、Continue 等插件通常在设置中提供以下字段：

```text
Provider: OpenAI Compatible
Base URL: https://nuoapi.net/v1
API Key:  YOUR_NUOAPI_API_KEY
Model:    MODEL_NAME_FROM_MODEL_PLAZA
```

完成后先测试单轮对话，再测试代码补全，最后才测试多文件编辑或自动执行。插件可能会额外发送系统提示词、工具定义和上下文文件，因此一次成功的短消息不能代表全部功能都可用。

### 7.2 VS Code 智能体

VS Code 里的"智能体"指 GitHub Copilot Chat 的 **Agent 模式**，Ask / Edit / Plan 同属这套 Chat 体验。

接入第三方模型走的是**自带密钥**（Bring Your Own Key，BYOK）：不登录 GitHub、也不买 Copilot 计划，就能把兼容端点加进语言模型选择器。

- BYOK 自 2025 年就已提供。
- 当前稳定版通过 **Custom Endpoint** 提供商配置；更早的版本叫 OpenAI Compatible，且一度只在 Insiders 提供。
- 与前面几节手写环境变量不同，VS Code 用的是可视化编辑器加一份 `chatLanguageModels.json`。

先记住三条边界，能省下大量排查时间：

- **BYOK 只管 Chat / Agent，不驱动行内代码补全、语义检索和 embeddings**，这些能力仍需要 GitHub 账号或 Copilot 支持。所以"聊天能用了"不等于"补全能用了"。
- **Agent 模式只列出支持工具调用的模型**（官方文档原文：模型要能用于 agent，必须支持 tool calling）。模型本身不支持工具调用时，填了也进不了智能体选择器；反过来硬填 `toolCalling: true` 而上游不支持，会在工具调用阶段报错。能力只按模型真实情况标。
- **本机 Custom Endpoint 与 GitHub 账号级 BYOK 是两条路**：本机端点（本节）支持 Chat Completions / Responses / Messages 三种 API 类型；在 GitHub.com 设置里给账号或企业连接 key 的 BYOK 目前只支持 OpenAI Chat Completions，配 Responses 端点不会工作（GitHub Changelog，2025-11-20，B 级）。两处配置不要混着理解。

> 依据：VS Code 官方《AI language models in VS Code》（code.visualstudio.com/docs/agent-customization/language-models）、官方博客《Use your own language model key in VS Code》（2026-06-18）与 Microsoft Learn《Configure VS Code custom endpoints》；**VS Code 文档核对窗口 2026-10-12，B 级**。涉及 NuoAPI 具体入口的路径沿用[协议科普](AI模型API协议科普-2026-10-12.md)记录的取证窗口 2026-09-21，本节未发起任何计费请求。

#### 7.2.1 用 Custom Endpoint 添加模型

前置：装好并能打开 VS Code 的 Chat 视图。

Copilot Business / Enterprise 用户需要管理员先在 GitHub.com 的 Copilot policy settings 里允许 **Bring Your Language Model Key in VS Code**，否则本机看不到加入入口。

1. 打开 Chat 视图，点模型选择器（当前模型名下拉）→ 齿轮图标 **Manage Language Models**；或按 `Ctrl+Shift+P` 打开命令面板，运行 **`Chat: Manage Language Models`**。
2. 在打开的 Language Models 编辑器里点 **Add Models** → 在提供商列表里选 **Custom Endpoint**（它取代了旧的 OpenAI Compatible provider；旧版 VS Code 里可能显示为 `OpenAI Compatible`，或需要手动写已弃用的 `github.copilot.chat.customOAIModels` 设置）。
3. 输入一个**分组名**（group name），例如 `NuoAPI`。它会出现在模型选择器和编辑器里，用来归纳这组模型。
4. 按提示输入模型显示名和 **API Key**（填 NuoAPI 的 Key）。VS Code 随后会打开 `chatLanguageModels.json`，让你补全模型细节。
5. 在打开的文件里按下表填 `apiType`、模型 `id`、`name`、`url` 和能力字段，保存。注意 **`url` 要填完整请求路径，不是第 1 节那种 Base URL 前缀**。
6. 回到 Chat 模型选择器，选中刚加的模型；要跑智能体就切到 Agent 模式再发任务。

#### 7.2.2 配置模板与三种 API 类型

`chatLanguageModels.json` 顶层是数组，一个 provider 一个对象：

```json
[
  {
    "name": "NuoAPI",
    "vendor": "customendpoint",
    "apiKey": "${input:nuoapiApiKey}",
    "apiType": "chat-completions",
    "models": [
      {
        "id": "MODEL_NAME_FROM_MODEL_PLAZA",
        "name": "MODEL_NAME_FROM_MODEL_PLAZA",
        "url": "https://nuoapi.net/v1/chat/completions",
        "toolCalling": true,
        "vision": false,
        "maxInputTokens": 128000,
        "maxOutputTokens": 8192
      }
    ]
  }
]
```

可直接复制的占位模板见 [`../examples/vscode-chatLanguageModels.json.example`](../examples/vscode-chatLanguageModels.json.example)。字段口径（VS Code 官方文档，B 级）：

- `vendor`：必须写 `customendpoint`。
- `apiKey`：保留 `${input:...}` 这种输入变量引用，让 Key 存在 VS Code 的凭据存储里，**不要把明文 Key 写进 JSON**（与第 2 节、第 12 节同一纪律）。
- `apiType`：provider 级默认值，可取 `chat-completions`（默认）、`responses`、`messages`；模型级同名字段可单独覆盖。
- 模型级 `id`：真正发给上游的模型名，照抄模型广场，**不要写别名**。
- 模型级 `url`：该模型的**完整**请求地址。
- `toolCalling` / `vision` / `maxInputTokens` / `maxOutputTokens`：按模型真实能力与上下文长度填写；agent 模式依赖 `toolCalling`。
- `thinking` / `supportsReasoningEffort` / `reasoningEffortFormat`：推理模型才填，不填不影响普通对话。
- `requestHeaders`：需要覆盖默认鉴权头时用。

三种 API 类型的完整地址（`model.url`）对应[协议科普](AI模型API协议科普-2026-10-12.md)中的协议分类：

| API 类型 | `model.url` 填什么 | 备注 |
| --- | --- | --- |
| Chat Completions | `https://nuoapi.net/v1/chat/completions` | 兼容面最广，接 NuoAPI 优先用它；默认发 `Authorization: Bearer <key>` |
| Responses | `https://nuoapi.net/v1/responses` | 仅当模型和分组确实支持 Responses 时选；入口同 `/v1` |
| Messages | `https://nuoapi.net/v1/messages` | Messages 入口是根地址拼接；鉴权头见下方注意 |

**鉴权头注意（C 级、未单点证实）**：VS Code 默认按 API 类型推断鉴权头——Messages 类型发 `x-api-key`，其余发 `Authorization: Bearer`。

而本仓库[第 5.1 节](#51-claude-code-与-claude-类工具)记录的 NuoAPI Messages 入口走的是 `ANTHROPIC_AUTH_TOKEN`（Bearer 形态）。两种头在 NuoAPI 上是否都接受，本节没有实测（不发起计费请求）。

若 Messages 类型返回 401，用 `requestHeaders` 显式改成 `Authorization: Bearer ${apiKey}` 后再测：

```json
"requestHeaders": { "Authorization": "Bearer ${apiKey}" }
```

#### 7.2.3 智能体模式与配套设置

- **工具调用是硬门槛**：`toolCalling: true` 且上游真的支持，模型才会出现在 Agent 模式的模型选择器里。
- **不登录 GitHub 时**，聊天标题、提交信息、重命名建议等后台小任务默认没有可用模型，需要把 `chat.utilityModel` 和 `chat.utilitySmallModel` 指到一个 BYOK 模型（选一个快而便宜的即可）。
- **补全、语义搜索、embeddings 不归 BYOK 管**：如果只想要这些能力，仍需 GitHub / Copilot。
- 想快速筛选，可在语言模型编辑器里用 `@provider:"NuoAPI"`、`@capability:tools`、`@capability:agent` 过滤。

#### 7.2.4 常见现象

| 现象 | 优先检查 |
| --- | --- |
| 模型选择器里找不到刚加的模型 | 分组名是否保存；JSON 是否已保存且语法正确；agent 模式要求 `toolCalling` 为真 |
| 找不到 Custom Endpoint / BYOK 入口 | VS Code 是否升级到含该功能的稳定版；Business / Enterprise 是否开了 BYOK 策略 |
| 请求返回 401 | `apiType` 与 `url` / 鉴权头是否配套；Messages 类型按上文改用 `requestHeaders`；Key 是否完整 |
| 请求返回 404 | `url` 是否误填成 Base URL 前缀；Chat Completions 是否带全 `/v1/chat/completions` |
| Agent 模式里模型可选但工具调用报错 | 模型真实能力不支持工具调用，或 `toolCalling` 误填为真 |
| 聊天能用但补全 / 语义搜索不可用 | BYOK 不覆盖这些能力，属预期行为 |

接完按[第 10 节](#10-最小验收流程)验收：先发一条只要求固定短句的普通对话，切到 Agent 模式做一次需要读文件或跑命令的任务，再到 NuoAPI 控制台核对调用记录与模型名。

### 7.3 其他 IDE 与编程助手

> **取证窗口 2026-10-06**，界面随版本变化，以你本机版本为准。

#### Qoder（国际版 IDE / Qoder CLI / Qoder CN）

同名产品有三种形态，能否接第三方网关**不一样**，先分清你用的是哪个：

| 形态 | 能否接？ | 依据 |
| --- | --- | --- |
| Qoder 国际版 IDE（qoder.com） | 支持 | 官方文档 docs.qoder.com |
| Qoder CLI（国际版与 CN 版，v1.1.50 起） | 支持 | 官方论坛公告 2026-09-12 |
| Qoder CN IDE 个人专业版（lingma.aliyun.com） | **不支持**，结论为「不匹配」 | 阿里云帮助中心，2026-07-03 |

### 形态一：Qoder 国际版 IDE

Settings → Models → 「+ Add」→ Custom Base URL。

Provider 选 OpenAI Compatible（再选 Chat Completions API 或 Responses API）或 Anthropic Compatible，然后填 Base URL、API Key、Model ID，点 Validate and Add。

### 形态二：Qoder CLI（v1.1.50 起）

1. 对话框输入 `/model`，Tab 切到 Custom 页。
2. 点 Add custom model（或按 `n`），选 OpenAI-compatible 或 Anthropic-compatible。
3. 依次填 Base URL → Model ID → 名称 → Key → 模型能力（上下文长度留空默认 128K，按模型实际值改）。
4. 保存后切到新模型，发条消息确认。

### 形态三：Qoder CN IDE 个人专业版——接不了

**截至帮助文档更新（2026-07-03），它只有百炼 / 智谱 / Kimi / MiniMax 四家预置提供商，没有任意 Base URL 入口。** 在这个入口里接 NuoAPI 的结论是「不匹配」，请改用 Qoder CLI，或等新版放开后再核实。

企业版另有一条路：管理员可在控制台「策略配置 → 推理服务配置」统一下发 URL、模型名与 Key。

### 前两种形态的填值

- OpenAI-compatible：Base URL `https://nuoapi.net/v1`，Key 用 NuoAPI Key，Model ID 照抄模型广场。
- Anthropic-compatible：Base URL 填根地址 `https://nuoapi.net`。

#### Trae CN（TRAE 国内版桌面端 / TraeCode）

1. 设置 → 模型 → 添加模型 → 选「自定义模型」（自定义模型仅桌面端提供；官方社区明确不支持接入本地模型）。
2. API 格式二选一：**OpenAI Chat Completions** 或 **Anthropic Messages**。
3. 「自定义请求地址」旁有**完整 URL 开关**：
   - 关闭开关（推荐）：只填基础地址，由 TraeCode 自己拼路径——OpenAI 格式填 `https://nuoapi.net/v1`，Anthropic 格式填根地址 `https://nuoapi.net`。
   - 打开开关：填完整路径，例如 `https://nuoapi.net/v1/chat/completions`。
4. 模型 ID 照抄模型广场，填 NuoAPI Key；高级配置（上下文窗口、图片输入等）按模型真实能力设置。保存后在对话框右下角**切换到该模型**——停留在 Auto / 内置模型上会误以为"配置没生效"。
5. 报 404 先怀疑完整 URL 开关两种填法搞反；报 400 先查 API 格式与模型 ID。

依据：Trae 官方文档《内置模型 & 自定义模型》（docs.trae.cn/ide_models，取证窗口 2026-10-06）。

## 8. MCP 工具

MCP Server 是本地工具扩展，例如文件系统、浏览器或数据库连接；它与模型 API 的 Provider 配置是两件事：

- 模型 API：负责生成模型响应，配置 Base URL、API Key 和模型名。
- MCP Server：负责提供本地工具，配置启动命令、参数和允许访问的目录。

不要把 MCP Server 的启动命令或本地目录填进 API Base URL。

Claude Desktop 的示例见 [`../examples/claude_desktop_config.json.example`](../examples/claude_desktop_config.json.example)。

只允许 MCP 访问必要目录，不要把包含密钥、浏览器 Cookie 或个人文件的目录直接暴露给工具。

## 9. 查询余额与额度

NuoAPI 这类 sub2api 形态的网关通常提供只读额度接口 `GET https://nuoapi.net/v1/usage`。鉴权与对话接口相同：Bearer 头，Key 不进 URL。

解析时注意两点：

1. **字段层级没有统一标准**（`remaining` / `quota.remaining` / `balance` 都出现过），要多级兜底。
2. **先校验 `Content-Type: application/json`**，否则 SPA 兜底会把 200 HTML 当成功。

完整的探路命令、JS/Python 兼容解析、错误码对照与取证记录模板已独立成篇：[`余额与额度查询-2026-10-06.md`](余额与额度查询-2026-10-06.md)。

该端点截至 2026-10-06 为 C 级证据（未单点实测），以实际响应为准。

## 10. 最小验收流程

每个工具至少完成以下检查：

1. 发一条只要求固定短句的请求。
2. 检查客户端没有持续重连、超时或静默降级。
3. 在服务控制台核对刚才的调用记录、模型名和时间。
4. 再测试该工具真正需要的能力，例如流式输出或工具调用。
5. 记录状态码、错误正文、模型名和时间；分享日志前删除 Key、Authorization header 和敏感输入。

“模型列表中出现”只说明列表接口返回了该名称，不等于当前 Key、分组和上游账号池一定能够成功调用。真伪或能力结论只能写成“匹配 / 不匹配 / 证据不足”，不能把没有出现某个关键词写成通过。

**计费提示**：多数客户端在建连、拉模型列表或首次交互时会先发若干探针请求，计费窗口内可能先产生少量 token。

**不要用一句 hello 的结果下"没有输入也在扣费"的结论**。改用工具自身的本地计费命令（如 Claude Code 的 `/cost`）或控制台使用记录核对。

## 11. 常见错误

按报错层级从上往下查，别跳着试。

### 11.1 鉴权与地址

- **`401 Unauthorized` / `{"code":"API_KEY_REQUIRED"}`**
  查 Key 是否完整、是否已撤销、变量名是否正确。Claude 系用 `ANTHROPIC_AUTH_TOKEN`，不是 `ANTHROPIC_API_KEY`。
- **`404 page not found`**
  请求落到了未注册路径。查 Base URL 是否多了或少了 `/v1`，或客户端拼出的完整路径不对。
- **`400 platform is not gemini` 等 platform/protocol 不匹配**
  协议选错，例如把 Gemini 原生地址填给了 OpenAI 客户端。Gemini CLI 的填法见[短页](Gemini-CLI-platform-is-not-gemini-2026-10-18.md)；其他客户端回[第 1 节](#1-按工具类型选择)速查表或[协议科普](AI模型API协议科普-2026-10-12.md)对照。
- **改完环境变量仍不生效**
  是否已新开终端 / 重启 GUI。Windows 用户级变量不会注入已运行进程。

### 11.2 模型与权限

- **`404 model_not_found` / `model not found`**
  模型名是否从当前账户列表逐字符复制；Key 分组是否含该模型；Codex 类工具是否选错 `wire_api`（Responses / Chat Completions）。
- **`400 requires an image model`**
  图片生成模型名前缀不在网关白名单，核对模型广场里的精确图片模型名。
- **`403` 或 `502`**
  当前分组、上游账号池和服务状态。保留错误正文后再联系服务方。

### 11.3 网络与本机

- **`ETIMEDOUT` / `ECONNRESET` / `socket hang up` / `fetch failed`**
  本机网络、代理与防火墙。这类字样与 Key、模型无关。
- **一直 `Reconnecting`**
  是否误启用 WebSocket（日志出现 `wss://.../v1/responses`），以及是否已完全重启客户端。

### 11.4 状态码之外的现象

- **客户端有回复但控制台无记录**
  是否实际用了另一个 Provider、环境变量或官方账户。
- **HTTP 200 但工具不可用**
  检查响应字段、工具调用结果和实际输出，不要只看状态码。
- **余额接口 200 但 `remaining` 为空**
  先看 `Content-Type`：可能是 SPA 兜底返回的 HTML，不是 JSON。字段结构见[余额与额度查询专篇](余额与额度查询-2026-10-06.md)。
- **启动就出现少量扣费 / 未输入也计费**
  客户端建连探针。先看工具本地计费命令（如 Claude Code 的 `/cost`）与控制台使用记录，不要用单句 hello 下结论。
- **想切换思考模式（Thinking）**
  Claude Code 终端内按 `Tab` 切换的说法来自公开教程，**C 级、未单点证实**。更稳妥的是按模型支持的推理等级在客户端设置里选。

### 11.5 路由缺失（不是你的配置问题）

这两条是**网关侧路由未挂载**，与 Key、模型名无关。记"该窗口不支持"，不要写成"模型不支持"——路由缺失与模型能力是两件事。

- **`POST /v1/embeddings` 返回 404**
  取证窗口 2026-09-21 该路由未挂载，返回 Gin 裸 404。换 Gemini 路径试探没有意义；需要向量能力时先重新探一次（零依赖脚本见 [`../examples/embeddings.py`](../examples/embeddings.py)）。
- **`POST /v1/audio/speech` 返回 404**
  取证窗口 2026-09-21 该路由未挂载（TTS 路由），同样是 Gin 裸 404。

## 12. 安全收尾

- 测试完成后撤销临时 Key，或限制额度和权限。
- 不要把真实配置文件复制进公开仓库；提交前运行 `git diff --check` 并检查敏感字符串。
- 发生 Key 泄露时立即撤销并重新创建，不要只修改本地文件。
- 不要把第三方网关当作官方服务；购买前单独核对价格、余额扣除、退款、隐私和故障转移规则。

相关模板和示例集中在 [`../examples/README.md`](../examples/README.md)，常见排错见 [`../FAQ.md`](../FAQ.md)。
