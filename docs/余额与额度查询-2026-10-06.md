## 1. 端点与鉴权

```text
GET https://nuoapi.net/v1/usage
Authorization: Bearer YOUR_NUOAPI_API_KEY
```

- 鉴权方式与对话接口完全相同：`Authorization` 头 + Bearer。**不要把 Key 拼进 URL 查询串**（会进代理日志、浏览器历史和 shell history）。
- 该接口只读取额度，不产生模型 token 消耗；但仍受网关的频次与风控约束，不要高频轮询。
- 路径因网关版本而异。若 `/v1/usage` 返回 404，说明当前版本可能未挂载此路由，改以控制台页面为准，**不要对一批候选路径做爆破式探测**。

## 2. 先探路，再写解析

动手写代码前，先用命令行看一次真实响应（连同响应头），确认状态码、`Content-Type` 和 JSON 层级：

```bash
curl -s "https://nuoapi.net/v1/usage" \
  -H "Authorization: Bearer YOUR_NUOAPI_API_KEY" -D -
```

```powershell
Invoke-WebRequest -Uri "https://nuoapi.net/v1/usage" `
  -Headers @{ Authorization = "Bearer $env:NUOAPI_API_KEY" } |
  Select-Object StatusCode, Headers, Content
```

把这一次的原始响应（**抹掉 Key 与响应头里的任何身份字段后**）留存为证据，记录取证日期。后续解析代码以这份真实结构为准，而不是以本文示例为准。

## 3. 字段没有统一标准：多级兜底解析

不同 sub2api 版本对"剩余额度"的摆法不同，常见的就有三种层级；单位与启用状态字段同理：

| 语义 | 可能出现的位置 |
|---|---|
| 剩余额度 | `remaining` / `quota.remaining` / `balance` |
| 计量单位 | `unit` / `quota.unit`（缺省按 `USD` 处理） |
| Key/账户是否启用 | `is_active` / `isValid`（缺省按 `true` 处理） |

### 3.1 JavaScript / TypeScript

```javascript
// request: GET {{baseUrl}}/v1/usage
// headers: { Authorization: `Bearer ${apiKey}` }
function extractUsage(response) {
  const remaining =
    response?.remaining ?? response?.quota?.remaining ?? response?.balance;
  const unit = response?.unit ?? response?.quota?.unit ?? "USD";
  return {
    isValid: response?.is_active ?? response?.isValid ?? true,
    remaining,
    unit,
  };
}
```

### 3.2 Python

```python
def extract_usage(resp: dict) -> dict:
    quota = resp.get("quota") or {}
    return {
        "remaining": resp.get("remaining", quota.get("remaining", resp.get("balance"))),
        "unit": resp.get("unit", quota.get("unit", "USD")),
        "is_active": resp.get("is_active", resp.get("isValid", True)),
    }
```

### 3.3 集成约定

1. 归一化后的结果作为客户端内**唯一**余额来源，不要让不同组件各自猜字段。
2. 多处展示同一余额时复用一次请求的结果，做 30–60 秒短期缓存；需要强一致的场景（提交大额任务前）再主动刷新一次。
3. 解析结果缺字段时显式标记为"未知"，**不要用 0 填充**——0 会被误读成"余额耗尽"并触发错误的停用逻辑。

## 4. 三个必须防的坑

1. **SPA 兜底假成功**。本仓库测试报告规范（[TEST_REPORT_SPEC.md](TEST_REPORT_SPEC.md)）记录过 `/v1/dashboard/billing/*` 返回 `200` 但响应体是前端 `index.html` 的情形。余额接口同理：**必须校验 `Content-Type` 含 `application/json`（或响应体能被 JSON 解析）后再解析**，否则 `remaining` 恒为空，且你可能误判为"额度没了"。
2. **数字不等于可消费量**。分组权限、`cache_read_input_tokens` 等缓存读取项照常收费、额度有效期、多个 Key 共享同一个钱包，都会让账面余额与实际体感不一致。能不能继续调用、扣了多少，以控制台账单明细和对话接口的 `usage` 字段为准。
3. **余额接口只证明"钱包"，不证明"模型可用"**。钱包有余额 ≠ 当前分组有权访问某个模型 ≠ 上游账号池健康。模型可用性仍要走最小测活（见[接入教程第 11 节「最小验收流程」](接入第三方工具教程-2026-09-26.md#11-最小验收流程)）。

## 5. 错误码对照

| 响应 | 含义与处理 |
|---|---|
| `200` + JSON | 正常，按第 3 节解析 |
| `200` + HTML | SPA 兜底，路由并不存在；不要解析，改查控制台 |
| `401` | Key 缺失/错误/已撤销；检查是否用了 Bearer 头 |
| `403` | Key 权限或 IP 限制 |
| `404` | 当前网关版本未挂载该路由，以控制台为准 |
| `429` | 查询也被限流；拉长轮询间隔 |
