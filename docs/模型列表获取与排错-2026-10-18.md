本文回答一个看起来很简单的操作：**我该往 `model` 字段里填什么名字？**

答案是"拉一份清单，逐字符照抄"。但这四个坑每一个都会让你以为是自己 Key 有问题。

素材来自仓库取证窗口 **2026-09-19 至 2026-09-21**，A 级（有原始响应体）。实例环境见 [`nuoapi.net`](https://nuoapi.net)。

---

## 1. 唯一正确的入口

```bash
curl -sS -H "Authorization: Bearer $NUOAPI_KEY" \
  https://nuoapi.net/v1/models
```

用 GET。**POST 会 404** —— 同一条路径只注册了 GET。

几个前提先记住：

| 事实 | 含义 |
| --- | --- |
| 这条路径**零成本** | 不发计费请求，随便拉 |
| 返回的是**你 Key 所属分组**的清单 | 不是全站清单 |
| 不存在"通用模型名表" | 别人清单里的名字，你的 Key 可能根本没有 |

换成更好读的输出：

```bash
curl -sS -H "Authorization: Bearer $NUOAPI_KEY" \
  https://nuoapi.net/v1/models \
  | python -c "import sys,json;[print(m['id']) for m in json.load(sys.stdin)['data']]"
```

---

## 2. 坑一：清单是**分组绑定**的

同一台网关，不同分组的 Key 拉到完全不同的表。取证窗口的实测样本：

| 分组 | `/v1/models` 条数 | 特点 |
| --- | ---: | --- |
| Codex 分组 | 4 | 只有 `codex-auto-review`、`gpt-5.6-luna`、`gpt-5.6-sol`、`gpt-6-astra` |
| free 分组 | 5 | 另一套名字 |
| grok 分组 | 7 | 多带 `owned_by:"xai"` 与 `supportsReasoningEffort` |
| gemini 分组 | 14（后一窗口 18） | **全是文本，没有任何图像模型** |
| image 分组 | 8 | 图像模型集中在这里 |
| anthropic 分组 | 4 | 都是非标准名 |

请求清单外的名字，会落到 `404 model_not_found`。

**实践结论**：不要按分组名猜模型，也不要抄别人的清单。**先跑一次 `/v1/models`，再决定填什么。**

---

## 3. 坑二：连字段形状都随分组变

这是最容易写错代码的地方。三把不同分组的 Key，返回的 JSON schema 互不相同：

| 字段 | Codex 分组 | gemini 分组 | grok 分组 |
| --- | --- | --- | --- |
| `id` | 有 | 有 | 有 |
| `display_name` | 有 | 有 | 有 |
| `owned_by` | 有（全 `openai`） | **无** | 有（`xai`） |
| `type` / `created_at` | 无 | 有，且 `created_at` 是**字符串** | 无 |
| `supportsReasoningEffort` | 无 | 无 | 有 |

所以：**别写只适配过一把 Key 的解析代码。** 下面这版能跑，是因为它对缺字段做了兜底：

```python
import json, os, urllib.request

req = urllib.request.Request(
    "https://nuoapi.net/v1/models",
    headers={"Authorization": "Bearer " + os.environ["NUOAPI_KEY"]},
)
with urllib.request.urlopen(req, timeout=30) as resp:
    payload = json.load(resp)

rows = []
for m in payload.get("data", []):
    rows.append({
        "id": m.get("id", ""),
        # 不要假设这些字段存在：按分组可能整个缺失
        "display": m.get("display_name") or m.get("id", ""),
        "owner": m.get("owned_by", "?"),
        "created": m.get("created") or m.get("created_at"),
    })

rows.sort(key=lambda r: r["id"])
for r in rows:
    print(f"{r['id']:44} {r['display']}")
print(f"\n共 {len(rows)} 个；owner 分布: "
      + ", ".join(f"{k}={v}" for k, v in
                  __import__('collections').Counter(r['owner'] for r in rows).items()))
```

## 4. 坑三：`/v1beta/models` 不是可路由清单

这是本文最值钱的一条，因为它**看起来能用**。

同一把 gemini 分组的 Key：

| 端点 | 返回条数 | 形状 |
| --- | ---: | --- |
| `/v1beta/models` | **5** | Google 形状，字段基本是 `null` |
| `/v1/models` | **14** | 网关形状，字段有值 |

而**实测能正常生成的 `gemini-2.5-flash`，只出现在那 14 个里。**

也就是说，你按 `/v1beta/models` 的 5 个名字去填，能用的那个可能根本不在列表上。结论：

> **取模型清单只认 `/v1/models`。** `/v1beta/models` 是 Gemini 原生接口的形状，不等于网关实际可路由的集合。

---

## 5. 坑四：列表里有 ≠ 你能调

这是最容易造成"我明明看到有这个模型"的困惑。

取证窗口的实证：anthropic 分组的 4 个模型**全部列在 `/v1/models` 里**，但逐个请求：

- `/v1/messages` → `502 Upstream access forbidden`
- `/v1/chat/completions` → `403 All available accounts exhausted`

**列表能拉到，上游账号池是空的。** 分组在售，但调不通。

所以看到某个模型却调不动时，先把错误分成三类，处理方式完全不同：

| 现象 | 层次 | 该怎么办 |
| --- | --- | --- |
| `404 model_not_found`，文案含 `in this group` | 分组不包含 | 重跑 `/v1/models` 核对名字，或换分组 Key |
| `403` / `502` | 上游账号池 | 不是你写错了，重试与改参数都没用 |
| `400` platform / protocol 不匹配 | 协议入口选错 | 换端点（见[协议科普](AI模型API协议科普-2026-10-12.md)） |

**注意错误文案有两套**，写客户端分支判断时不能只认一种：

| 分组 | 文案 | 字段 |
| --- | --- | --- |
| grok | `Model "X" is not supported by any configured account in this group` | `type: model_not_found` |
| 其余 | `Model "X" is not available for this group` | `code: 404` / `status: NOT_FOUND` |

只按 `type` 或只按 `code` 判错的代码，会漏掉一半情况。

## 6. 别用 `/v1/models/{id}` 反查上游

单模型详情路由**存在**（`GET /v1/models/{id}` 返回 200），但它的元数据是硬编码占位：

```jsonc
{"id":"gemini-3-pro-image", "created":1704067200, "owned_by":"openai", "display_name":"gemini-3-pro-image"}
{"id":"grok-imagine-image", "created":1704067200, "owned_by":"openai", "display_name":"grok-imagine-image"}
{"id":"gpt-6-astra",        "created":1788480000, "owned_by":"openai", "display_name":"GPT-6 Astra"}
```

三个问题：

1. **`owned_by` 不可信。** Gemini 与 Grok 的模型都写 `openai`。同一个 `grok-4.5` 在 free 分组回 `openai`、在 grok 分组回 `xai` —— 它是**按分组配的**，不是事实。
2. **`created` 是占位值**，多为 `1704067200`（2024-01-01）。
3. **没有任何价格、`supported_parameters`、provider 字段。**

想靠这个端点反查上游是死路（取证时试过，负结果）。**任何按 `owned_by` 分支的客户端代码也会分错。**

## 7. 顺序：先清单，再挑模型，再验一个

一个不会白花钱的流程：

1. **拉清单**：`GET /v1/models`（零成本）。
2. **挑一个**你要用的模型名，**逐字符**复制（大小写、连字符、日期后缀都别改）。
3. **发一条最小请求**，只要固定短句回复。这一步会花钱，但只花几分钱。
4. **到控制台核对调用记录**：模型名对不对、用量是否合理。
5. 确认无误后再进正式流程。

**不要为了"试一遍"把清单里的模型挨个打一遍** —— 那是纯烧钱，而且 `403`/`502` 那类失败往往根本不计费也不给你信息。

---

## 8. 图像模型要单独确认

`/v1/models` 里没有 `gpt-image-*`，就说明这把 Key 出不了图 —— 图像能力集中在 image 分组。

但**列表里有图像模型，也不等于那个端点能用**。

取证窗口实测：`gemini-*-image` 明明列在分组里，打 `/v1/images/generations` 仍被
`400 images endpoint requires an image model` 拒绝。

原因不是权限，是**协议走错了**——它们要走 Gemini 原生协议，不是 OpenAI images 端点。细节见[《图片生成实测教程》](图片生成实测教程-2026-09-28.md)。

## 9. 小结

| 要点 | 一句话 |
| --- | --- |
| 入口 | `GET /v1/models`，POST 会 404，零成本 |
| 范围 | 按 Key 分组返回，不存在通用表 |
| schema | 随分组变，解析必须兜底 |
| 别用 | `/v1beta/models` 当能力清单；`/v1/models/{id}` 当上游证据 |
| 最大的坑 | 列表里有 ≠ 能调用，先发一条最小请求验证 |

知道自己要的模型在不在这把 Key 里之后，下一步是判断**它到底是不是真的**——那属于另一件事，见[《模型真伪与防掺水检测方法学》](MODEL_VERIFICATION_METHODS.md)，结论只用「匹配 / 不匹配 / 证据不足」三态。
