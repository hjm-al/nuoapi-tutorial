地址夹具是 [`nuoapi.net`](https://nuoapi.net)，模型 ID 与分组以[模型广场](https://nuoapi.net/model-plaza)和控制台实时显示为准。

很多开发者部署或使用了开源 Web 聊天客户端（如静态托管在 GitHub Pages、Vercel 或本地运行的 NextChat、LobeChat、Chatbox、LibreChat），在接入中转 API 调用 DeepSeek、OpenAI 或 Gemini 等模型时，容易遇到跨域、路径重复或模型未映射等问题。本文整理 5 大高频长尾症状与排查方法。

---

## 1. 30 秒症状分流对照表

| 症状表现 | 控制台/网络报错 | 根本原因 | 最短修复动作 |
|---|---|---|---|
| 点击发送立即红字，无响应 | `Failed to fetch` / `CORS error` | 浏览器跨域策略拦截纯静态前端直连 | 改用带服务端反代的部署，或使用桌面端 |
| 提示页面不存在或接口 404 | `404 Not Found`（含 `/v1/v1`） | 客户端自动追加路径导致 Base URL 重复拼接 | 检查 Network 请求地址，去掉 Base URL 末尾的 `/v1` |
| 下拉菜单无模型或报不存在 | `404 model_not_found` | 客户端未配置自定义模型，或模型 ID 未照抄 | 客户端加 `+` 开启模型，模型 ID 逐字符对齐模型广场 |
| 打字机不流式，整段憋出 | `stream failed` / 延迟十几秒突然弹出 | 中间反代或代理缓存了 SSE 数据流 | 反代关闭缓冲（`proxy_buffering off`） |
| 发送带图问题报 400 | `400 invalid request` / `image format` | Base64 图片体积超限或多模态协议不匹配 | 压缩图片到 1024 宽/高以内，核对是否包含视觉模型 |

## 2. 5 大长尾问题排查与修复

### 2.1 浏览器报跨域拦截（`Failed to fetch` / `CORS error`）

**症状**：如果你的聊天前端是托管在 GitHub Pages（如 `xxx.github.io`）或纯静态 HTML，填入 Base URL 和 Key 点击发送后，立即弹出红字 `Failed to fetch` 或 `Network Error`。按 F12 打开浏览器开发者工具，控制台显示：
`Access to fetch at 'https://nuoapi.net/v1/chat/completions' from origin 'https://xxx.github.io' has been blocked by CORS policy`。

**原因**：纯前端 SPA（单页应用）运行在浏览器沙箱内，跨域发起包含自定义 Header（`Authorization: Bearer ...`）的请求时，浏览器会先发送 `OPTIONS` 预检请求。如果中转网关未对当前前端域名开放 CORS 头，就会被浏览器强制中断。

**解法**：
1. **优先推荐带后端的部署方式**：NextChat 或 LobeChat 官方推荐使用 Docker 或 Vercel 部署。在此模式下，Web 页面只向自己的后端路由发请求，再由 Node.js 服务端发起 API 调用，完全避开浏览器同源策略。
2. **改用桌面客户端验证**：下载安装 Chatbox 或 Cherry Studio 桌面端。桌面环境不受浏览器 Web CORS 限制，可直接用于排查是否为跨域问题。

### 2.2 Base URL 路径重复拼接（`404 Not Found` / `/v1/v1` 陷阱）

**症状**：填好地址和 Key，点击发送报 `404 Not Found`。

**原因**：不同的 Web 聊天客户端对“接口地址 / Base URL”的定义不一致：
- **NextChat (ChatGPT-Next-Web)**：部分版本的“接口地址”输入框会自动补齐 `/api/openai/v1` 或 `/v1`。如果你填了 `https://nuoapi.net/v1`，最终发出的请求就会变成 `https://nuoapi.net/v1/v1/chat/completions`，网关路由匹配不到，返回 404。
- **LobeChat / Chatbox**：通常要求显式填入完整前缀 `https://nuoapi.net/v1`。

**核对标准**：
按 F12 切换到“网络（Network）”选项卡，看发出的 POST 请求地址：
- 正确终点必须是：`https://nuoapi.net/v1/chat/completions`；
- 如果抓包看到 `https://nuoapi.net/v1/v1/chat/completions`，把客户端设置里的 Base URL 改为 `https://nuoapi.net`；
- 如果抓包看到 `https://nuoapi.net/chat/completions`（少了 `/v1`），在 Base URL 补上 `/v1`。

### 2.3 自定义模型未映射或模型不存在（`model_not_found`）

**症状**：在客户端下拉菜单里找不到 `deepseek-chat`、`deepseek-v4.1-flash` 或 `gemini-2.5-flash`；或者在自定义输入框填入后，调用报错 `model_not_found`。

**原因与语法规范**：
1. **NextChat 的模型增减语法**：NextChat 默认只展示部分内置模型。要添加第三方模型，在“设置”→“自定义模型”中，必须用 `+` 前缀，多个模型用逗号隔开，例如：
   ```text
   -all,+deepseek-v4.1-flash,+gemini-2.5-flash,+gpt-6-astra
   ```
   （`-all` 表示清空内置无关模型，`+模型名` 表示显式加入列表）。
2. **模型 ID 逐字符核对**：不要填简写。例如你的 Key 在国模分组，模型名应照抄当前清单中的精确名字（如 `deepseek-v4.1-flash`），不要写成 `deepseek` 或 `deepseek-v3`。若跨分组调用未购买或未授权的模型，网关会直接返回 404。

### 2.4 流式打字机不逐字输出（SSE 缓冲与卡顿）

**症状**：发消息后光标一直转圈，完全不逐字打印，等待 10~20 秒后整段回复一次性弹出来；或者中途报错 `stream connection closed abnormally`。

**原因**：Server-Sent Events (SSE) 协议依赖长连接逐字推送数据块。如果你的客户端和中转站之间存在自建反向代理（如 Nginx）、CDN 或某些本地代理工具，中间层开启了代理缓冲（Buffer），会攒满 4KB 甚至更多数据后才统一刷新，导致流式打字机失效。

**解法**：
若有自建 Nginx 反代，在代理规则中加入禁用缓冲配置：
```nginx
proxy_buffering off;
proxy_cache off;
proxy_set_header X-Accel-Buffering no;
proxy_set_header Connection '';
proxy_http_version 1.1;
chunked_transfer_encoding on;
```
如果使用本地代理工具，可尝试将中转域名加入直连列表。

### 2.5 多模态与图片输入报 400（Invalid image payload）

**症状**：在 Web 聊天端上传图片并搭配 `gemini-2.5-flash` 或视觉模型提问时，返回 `400 invalid request`。

**原因**：
- Web 聊天端上传本地图片通常会将其转为 Base64 编码内联进 JSON（形如 `data:image/png;base64,...`）。如果图片原始体积较大（例如手机实拍图 5MB），Base64 编码后膨胀约 33% 达到近 7MB，容易触发网关的反代报文上限或上游解析超时。
- 另外，部分模型属于纯文本分组，不支持 Vision 视觉输入。

**解法**：
1. 上传前将图片缩放压缩至 1024×1024 分辨率、1~2MB 以内；
2. 确认你选择的模型支持视觉多模态能力，且当前 Key 所在分组包含该模型。

## 3. 5 分钟排查验证流程

如果 Web 聊天端报错，按以下顺序 3 步排查，快速判断是客户端配置问题还是网关问题：

### 第 1 步：用 curl 绕过前端，验证 Key 与可用模型

在本地终端运行：
```bash
curl -sS https://nuoapi.net/v1/models \
  -H "Authorization: Bearer YOUR_NUOAPI_API_KEY"
```
如果返回模型列表 JSON，说明网络和 Key 正常，记下列表中确切的模型 `id`。如果报 401，参考 [401 排错页](401-invalid-api-key.md)。

### 第 2 步：发一条最小单轮对话请求

```bash
curl -sS https://nuoapi.net/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_NUOAPI_API_KEY" \
  -d '{
    "model": "deepseek-v4.1-flash",
    "messages": [{"role": "user", "content": "ping"}]
  }'
```
（请将 `deepseek-v4.1-flash` 替换为你分组里实际有的模型 ID）。如果终端能正常收到回复，说明服务端完全正常，问题 100% 在 Web 客户端的 URL 拼接或跨域设置上。

### 第 3 步：核对 Web 客户端的 Network 请求

回到 Web 聊天界面，按 F12 打开网络面板，发一条消息：
- 查看实际发出的 Request URL 是否为标准的 `https://nuoapi.net/v1/chat/completions`；
- 查看 Status 状态码（404 查路径，401 查 Key，CORS 查前端部署形态）。
