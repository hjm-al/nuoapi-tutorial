# AI 模型 API 协议科普

> 本文是独立开发者维护的技术说明，与 OpenAI、Anthropic、Google、xAI、DeepSeek、MiniMax 或其他模型厂商不存在官方关联、投资、赞助或合作关系。文中商标和产品名称仅用于协议兼容性说明。
> 本仓库不提供、不代售任何 API 服务或充值通道。
> 使用第三方服务前，请自行核对服务条款、隐私政策、价格和可用性。

本文只解释 AI 客户端常见的 API 协议、地址结构和判断方法，不讲具体工具如何安装。要配置 Claude Code、Codex、VS Code、Cursor、ZCode 等工具，请看[《接入第三方工具教程》](接入第三方工具教程-2026-09-26.md)。

## 1. 先分清模型、厂商与协议

这三个概念经常被混在一起：

- **模型**：实际生成内容的模型，例如某个 GPT、Claude、Gemini、Grok、DeepSeek 或 MiniMax 模型。
- **厂商**：提供模型或 API 服务的公司。
- **协议**：客户端与服务端交换请求和响应时采用的路径、字段和数据结构。

同一模型可能通过不同协议提供，同一种协议也可以承载不同厂商的模型。因此，接入第三方网关时不能只看模型或厂商名称，必须看客户端实际发送哪种协议。

xAI、DeepSeek、MiniMax 等厂商的接口通常复用现有兼容形态，并不会因为厂商不同就自动产生一种新的报文协议。

## 2. 四种常见协议

面向通用文本与 Agent 客户端，常见协议可归纳为四类：

| 协议 | 典型路径 | NuoAPI Base URL | 常见使用场景 |
| --- | --- | --- | --- |
| **Chat Completions** | `/v1/chat/completions` | `https://nuoapi.net/v1` | 大多数 `OpenAI Compatible` 客户端、IDE 插件和脚本 |
| **Responses** | `/v1/responses` | `https://nuoapi.net/v1` | Codex 等明确声明使用 Responses 的新工具 |
| **Messages** | `/v1/messages` | `https://nuoapi.net` | Claude Code、Anthropic Compatible 客户端 |
| **Gemini 原生** | `/v1beta/models/{模型名}:generateContent` | REST 通常为 `https://nuoapi.net/v1beta` | Gemini CLI、直接调用 Generative Language API 的脚本 |

表中的 NuoAPI 路径依据仓库取证窗口 **2026-09-21 01:30 UTC**。模型、分组和入口可能变化，使用时仍应以当前[模型广场](https://nuoapi.net/model-plaza)、账户控制台和实际返回为准（实例站点：[`nuoapi.net`](https://nuoapi.net)）。

## 3. Chat Completions

Chat Completions 是目前兼容面最广的经典对话协议。请求通常包含：

- `model`：模型 ID。
- `messages`：按角色排列的消息数组。
- `stream`：是否流式返回。
- `tools`：可选的工具定义。

它的典型完整请求地址是：

```text
https://nuoapi.net/v1/chat/completions
```

工具若要求填写 **Base URL**，通常填：

```text
https://nuoapi.net/v1
```

工具若明确要求 **Endpoint、完整 URL 或自定义请求地址**，才填完整的 `/v1/chat/completions` 地址。

看到 `OpenAI Compatible` 只能说明工具大概率采用这一协议，不能证明所有高级能力都兼容。工具调用、图片输入、结构化输出和流式响应仍需分别验证。

## 4. Responses

Responses 与 Chat Completions 共用 `/v1` 前缀，但请求和响应结构并不相同：

```text
https://nuoapi.net/v1/responses
```

常见识别信号包括：

- 配置中出现 `wire_api = "responses"`。
- 工具文档明确写 `Responses API`。
- 日志请求路径为 `/v1/responses`。

不能因为两者使用同一个 Base URL 就随意互换。选错后可能出现路径 404、字段 400、流式异常或客户端持续重连。

部分客户端还会优先尝试 WebSocket。以当前仓库记录的 Codex 配置为例，需要设置 `supports_websockets = false`，让客户端使用 HTTP Responses；否则可能持续显示 `Reconnecting`。这属于客户端传输方式，不是第五种模型协议。

## 5. Messages

Messages 是 Anthropic 兼容客户端常用的协议，完整请求路径为：

```text
https://nuoapi.net/v1/messages
```

它最容易出错的地方是 Base URL。对会自行拼接 `/v1/messages` 的客户端，应填根地址：

```text
https://nuoapi.net
```

如果误填 `https://nuoapi.net/v1`，客户端可能继续拼成错误路径并返回 404。

常见环境变量是：

```text
ANTHROPIC_BASE_URL=https://nuoapi.net
ANTHROPIC_AUTH_TOKEN=YOUR_NUOAPI_API_KEY
```

不同客户端可能使用 `x-api-key` 或 `Authorization: Bearer`。鉴权头不能只凭协议名称猜测，应以客户端文档、网关要求和实际响应为准。

## 6. Gemini 原生协议

Gemini 原生协议的路径包含模型名和动作：

```text
https://nuoapi.net/v1beta/models/{模型名}:generateContent
```

直接使用 REST 或脚本时，Base URL 通常是：

```text
https://nuoapi.net/v1beta
```

Gemini CLI 是配置层面的例外。它会自行拼接版本和模型路径，因此环境变量填写根地址：

```text
GOOGLE_GEMINI_BASE_URL=https://nuoapi.net
GEMINI_API_KEY=YOUR_NUOAPI_API_KEY
GEMINI_MODEL=MODEL_NAME_FROM_MODEL_PLAZA
```

出现 `400 platform is not gemini` 一类错误时，应优先检查入口和协议平台是否匹配，而不是先认定 Key 无效。

## 7. Base URL 与完整请求地址

这是接入时最常见的混淆。

**Base URL 是前缀**，客户端会继续拼接协议路径。例如：

```text
Base URL: https://nuoapi.net/v1
客户端拼接: /chat/completions
最终请求: https://nuoapi.net/v1/chat/completions
```

**完整请求地址已经包含最终路径**，客户端不应再次拼接：

```text
https://nuoapi.net/v1/chat/completions
```

判断字段含义时，按以下顺序核对：

1. 字段标签是否明确写 `Base URL`、`API Base` 或 `base_url`。
2. 是否存在“完整 URL”“Custom endpoint”或“由客户端自动拼接路径”的开关。
3. 查看客户端日志中的最终请求路径。
4. 返回 404 时先检查路径，不要反复更换 Key。

## 8. 如何判断客户端使用哪种协议

优先使用有判别力的信号：

| 信号 | 可作出的判断 |
| --- | --- |
| 文档明确写 Chat Completions、Responses、Messages 或 Gemini API | 直接按文档选择 |
| 配置出现 `wire_api = "responses"` | Responses |
| 配置出现 `openai-chat-completions` / `openai-completions` | Chat Completions |
| 配置出现 `anthropic-messages` | Messages |
| 日志出现最终请求路径 | 按路径确认实际协议 |
| 只有厂商名称或模型名称 | 证据不足，不能据此判断协议 |

客户端界面中出现某个模型名，只能说明列表或配置里存在这个名称，不能证明当前 Key、分组和上游账号池一定能够调用成功。

## 9. MCP 不是模型 API 协议

MCP（Model Context Protocol）负责把文件系统、浏览器、数据库等工具提供给模型或 Agent；模型 API 负责生成响应。两者配置位置和作用不同：

- 模型 API 配置地址、Key、模型名和报文协议。
- MCP Server 配置本地启动命令、参数和允许访问的资源。

MCP Server 的启动命令或本地目录不能填进模型 API 的 Base URL。

## 10. 协议兼容不等于能力兼容

请求返回 HTTP 200，只能说明这一请求得到了成功响应，不能自动证明以下能力可用：

- 工具调用。
- 图片或文件输入。
- 流式输出。
- 联网搜索。
- 长上下文。
- 结构化输出。
- embeddings、语音或图片生成等独立路由。

这些能力需要检查响应字段和实际结果。模型真伪或能力结论统一使用 **匹配 / 不匹配 / 证据不足**，不能把“没出现某个厂商关键词”“响应很快”或“列表里有模型名”当成通过证据。

## 11. 接下来怎么配置

已经确认协议后，再进入[《接入第三方工具教程》](接入第三方工具教程-2026-09-26.md)，按工具类型选择：

- 图形客户端。
- 命令行客户端。
- IDE 插件与智能体。
- Provider 配置管理器。
- MCP 工具。
- 有特殊限制的新兴客户端。

配置完成后必须做最小测活，并到服务控制台核对模型名、调用时间和记录。协议解释解决的是“应该怎么说话”，工具教程解决的是“在哪里填写”。
