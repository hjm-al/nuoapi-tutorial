连续做图像生成时有个普遍问题：**每次的失败点都被随手忘掉，提示词因此永远停在第一版。**

本文给出一套闭环。它不追求"记录得多"，只追求一件事——**让下一次修改有依据，且能验证改对了没有**。

```
① 采集            ② 归纳              ③ 修订              ④ 验证
生成结束即记录  →  到期聚类       →  改提示词升版本  →  对照实验
质量事件.jsonl     复盘报告          版本登记(哈希)      验证记录
     ↑                                                    │
     └──────────── 有效则采纳为默认，无效则回退 ←──────────┘
```

**成本边界**：①②③ 全部离线，不产生任何请求与费用，随时可做。**只有 ④ 的对照实验会计费**，必须先立方案、写明请求数与预估金额，拿到明确授权再跑。

---

## 1. 两类记录，别混写

| 记录 | 回答什么 | 性质 |
| --- | --- | --- |
| **运行记录** | 这次请求发生了什么：模型、参数、HTTP 状态、返回字段形态、实际尺寸、耗时、输出路径、错误正文 | 客观事实 |
| **质量事件** | 这张图好在哪、差在哪、该改提示词哪一段 | 主观评审 |

运行记录用 JSON 原样存（本仓库的 [`图片生成实测教程`](图片生成实测教程-2026-09-28.md) 就是这个用法，实例环境见 [`nuoapi.net`](https://nuoapi.net)）。质量事件是本文新增的部分——它要能**聚类**，所以必须结构化。

---

## 2. 缺陷代码化：C1–C10

不用自由文本写"这图不好看"，而是从固定代码里选。只有这样，不同时间的记录才能统计。

### 2.1 内容类（对应提示词的主体 / 细节 / 约束段落）

| 代码 | 名称 | 可观察表现 |
| --- | --- | --- |
| `C1` | 主体错位 | 画成了别的东西；道具被画成幻想生物或普通物件；主体数量错误 |
| `C2` | 结构缺陷 | 肢体、手指、关节、道具连接处断裂或畸变；透视错误；同一主体重复出现 |
| `C3` | 事实错误 | 材质、服饰、道具用途、场景年代与事实不符（如编织道具画成塑料） |
| `C4` | 文字污染 | 出现乱码文字、水印、无关 Logo、签名 |

### 2.2 画面控制类（对应构图 / 风格 / 光线 / 色彩段落）

| 代码 | 名称 | 可观察表现 |
| --- | --- | --- |
| `C5` | 构图失控 | 主体过大或过小、被裁切、重心偏移、留白区被占用或不足 |
| `C6` | 材质细节缺失 | 纤维、绳结、纹理、毛发不可辨；画面发糊；细节被平滑掉 |
| `C7` | 风格冲突 | 同时出现两种媒介语言（摄影＋卡通）；风格与用途不符 |
| `C8` | 光线 / 色彩偏移 | 明显偏色、过曝、暗部死黑、饱和度过高或过低 |

### 2.3 规格 / 流程类

| 代码 | 名称 | 说明 |
| --- | --- | --- |
| `C9` | 规格不符 | 实际尺寸、格式与请求不一致；文件损坏；返回体缺字段 |
| `C10` | 平台失败 | 502 / 404 / 超时 / 鉴权失败 / 响应里没有图像字段 |

**`C9` 与 `C10` 不进入提示词修订。** 上游抖动不是你提示词的问题，把它写成提示词规则属于典型错误归因；规格不符先查脚本与参数。

---

## 3. 归因到提示词段落

每条缺陷必须填 `suspect_clause`，取值限定为模板里的十个段落：

`用途` · `主体` · `场景` · `细节` · `构图` · `风格` · `光线` · `色彩` · `文字留白` · `约束`

这样修订能直接定位到"要改哪一行"，而不是重写整段提示词。**这也是整套方法里最省时间的一步**：填不出 `suspect_clause`，说明这条缺陷还没想清楚，先别记。

---

## 4. 同时记正面证据

每条记录除缺陷外必须有 `positives`：这次做对了什么。

没有它，第 ④ 步的回归检查无从做起——你不知道新版本是否破坏了旧版本已经做对的部分。**只记问题的方法会越改越偏。**

最小字段集（能在 2 分钟内写完，否则会被跳过）：

```json
{
  "id": "QE-20261018-001",
  "theme": "<主题名>",
  "model": "gpt-image-2.5",
  "prompt_version": "v3",
  "result": "success",
  "defects": [{"code": "C6", "clause": "细节", "note": "编织纹理在中景处糊成一片"}],
  "positives": ["主光源方向正确", "留白区未被占用"],
  "severity": "S2"
}
```

- 唯一事实源是 append-only 的 JSONL，**永不改写历史行**。
- 人可读版本另存 Markdown，但不作为事实源；两者冲突以 JSONL 为准。
- 写入时机：生成结束、看过图之后**立刻**写。攒到复盘时凭记忆补写，记忆会美化结果。

严重度分四档：`S0`（不可交付，必须立即复盘）→ `S1`（影响用途）→ `S2`（可修可发）→ `S3`（吹毛求疵）。

## 5. 复盘触发条件

满足任一即到期，不要凭感觉"差不多了":

| 类型 | 触发条件 | 说明 |
| --- | --- | --- |
| 时间 | 距上次复盘 ≥ **14 天** | 兜底，防止低频使用长期不校准 |
| 数量 | 相同主题自上次复盘新增 **≥ 5 条** | 样本够了才有统计意义 |
| 复现 | 相同「主题 + 缺陷代码」累计 **≥ 3 次** | 单次是随机波动，3 次才可能是系统性缺陷 |
| 阻断 | 出现任意 **S0** | 立即复盘，不等周期 |
| 交付前 | 即将对外交付，或要换模型 / 开新主题 | 强制校准一次基线 |

**模板升级的门槛更高**：通用模板影响所有未来主题，只有同一缺陷代码**跨 ≥ 2 个主题出现、且全局累计 ≥ 4 次**时才建议改模板。单主题反复出现的，只改该主题自己的提示词。

这条规则的用意很直接：**防止把一个主题的特例污染成全部默认。**

复盘产出两份：

1. 复盘报告：按缺陷代码聚类，给频次、样例、归因段落、**建议改动清单**——每条改动必须写明依据哪些事件 ID。
2. 若采纳：更新提示词 → 登记新版本 → 在台账追加一条记录（采纳了什么、拒绝了什么）。

## 6. 提示词版本用内容哈希登记

**不要把版本号写进提示词正文。** 脚本通常把整个文件内容当 `prompt` 发给模型，`# v3` 这类字样会污染输入。

正确做法是单独维护一份版本登记表，存**内容哈希**：

```json
{
  "themes": {
    "<主题名>": {
      "current": "v3",
      "versions": [
        {"v": "v2", "sha256_12": "a1b2c3d4e5f6", "changed": "补充材质描述", "evidence": ["QE-20261018-001"]},
        {"v": "v3", "sha256_12": "f6e5d4c3b2a1", "changed": "拆开约束段", "evidence": ["QE-20261018-004"]}
      ]
    }
  }
}
```

哈希用正文前 12 位即可，够区分。它的作用是对账：**任何时候都能验证"当时跑的那版"到底是哪份文本**，而不依赖文件名或人的记忆。

## 7. 验证：对照实验，只改一个变量

改了提示词不等于变好了。验证必须是对照实验。

**实验设计**

- 固定：模型、尺寸、质量、输出格式、主题。
- 唯一变量：提示词 `v(n)` 对 `v(n+1)`。
- 对照组正文从版本登记表找到哈希后取回，重跑一次。
- 样本量：每个版本至少 **2 张**，或 2 个模型各 1 张。**单张图的差异不能作为证据。**
- 本步计费，先立方案等授权。

**四项量化指标**

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 目标缺陷复现率 | 该缺陷在 v(n+1) 组出现的图片数 ÷ 总图数 | 相对基线下降 ≥ 50%，或降为 0 |
| 回归率 | v(n+1) 组**新出现**的缺陷条数 | 必须为 **0**，否则不算净改善 |
| 健康项保持率 | 基线的 `positives` 在新版本中仍成立的比例 | ≥ 80% |
| 规格合规率 | 实际尺寸 / 格式与请求一致的比例 | 恒为 100%（不达标属 C9，与提示词无关） |

**判定表**

| 目标缺陷下降 | 回归 | 结论 |
| --- | --- | --- |
| 是 | 无 | 采纳为新默认版本 |
| 是 | 有 | 有条件采纳：只留有效条款，回退引发回归的部分，重测 |
| 否 | 无 | 无收益，回退；原因记入台账，可能是随机性 |
| 否 | 有 | 立即回退，并把该改动标记为**已证伪**，避免以后重复尝试 |

**归因纪律**：同一改动在**两个及以上样本**上同向才算证据。单个样本的差异只记为"待验证观察"——写进台账，但不得据此改默认提示词。这条是为了避免把模型随机性当成规律。

---

## 8. 防退化四条硬约束

持续迭代最大的风险不是不优化，而是**把提示词越改越肿、越改越偏**。

1. **不满 3 次不动手**。同一缺陷代码在同一主题出现不足 3 次时，只能记录候选改动，不得改默认提示词。
2. **修订必须可回滚**。改动前把旧版正文存档。没有可回滚的旧版，就不算完成修订。
3. **提示词有长度上限**。正文超过约 2000 字符时，本次修订必须同时删掉一些内容，或书面说明为什么不删。只增不减的提示词最终会自相矛盾。
4. **不把平台问题写进提示词**。`C10` 一律不进修订清单。

---

## 9. 与"模型真伪"的关系

这两件事容易混，但回答的问题不同：

- **本文**：同一模型下，我的提示词怎么写才稳定产出我要的画面。
- [**模型真伪与防掺水检测方法学**](MODEL_VERIFICATION_METHODS.md)：我付费调用的到底是不是它声称的那个模型。

如果连模型都可能是假的，先做真伪判定再谈提示词优化——**在一个不确定的模型上优化提示词，结论不可迁移。** 真伪结论只用「匹配 / 不匹配 / 证据不足」三态。
